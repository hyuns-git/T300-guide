# 06. 엘리베이터 층간 이동 계획

이 문서는 아직 구현하지 않은 부분의 계획입니다. 직접 확인한 사실과 추정을 구분해서 적습니다.

## 지금 알고 있는 것

- 푸두 T300 제품 소개 자료에는 엘리베이터 제어 모듈과 IoT 연동(엘리베이터, 출입 게이트, 소프트웨어 API)이 언급됩니다. 층을 옮기는 구체적인 절차는 자료에 없습니다.
- 푸두는 일본 Nippon Otis Elevator의 Integrated Dispatch API와 클라우드로 연동해 다른 모델인 FlashBot의 층간 이동을 구현한 사례가 있습니다. 출처는 [Automated Warehouse 기사](https://www.automatedwarehouseonline.com/pudu-robotics-successfully-integrates-flashbot-with-elevators/)입니다. T300이 같은 방식인지는 확인하지 못했습니다.
- 직접 조회해서 본 것(04 문서): 한 매장에 1층 맵과 3층 맵이 따로 등록돼 있었고, 3층 맵의 `elements`에 이름이 `Elevator`인 `gate` 요소가 있었습니다. 맵에 엘리베이터가 표시돼 있다는 근거이지만, 이 요소로 엘리베이터가 실제로 호출되는지는 확인하지 못했습니다. 1층 맵에도 같은 요소가 있는지는 현재 맵 하나만 조회되는 탓에 아직 못 봤습니다.
- 푸두 오픈플랫폼 문서 사이드바에는 Robot task, Robot Scheduling, Control command 같은 항목이 있습니다. 본문은 아직 읽지 않았습니다.

## 가장 먼저 정할 것: 엘리베이터를 누가 부르는가

- **경로 A.** 푸두 클라우드와 로봇이 엘리베이터 연동을 알아서 처리한다. 우리는 다른 층의 지점을 목적지로 주기만 한다. 푸두 쪽 엘리베이터 모듈 설치와 건물 쪽 연동이 이미 되어 있어야 한다.
- **경로 B.** 우리 서버가 건물이나 승강기 업체가 제공하는 로봇 연동 API로 엘리베이터를 부르고, 푸두 API로 로봇의 이동 시점을 맞춘다. 상태 머신을 직접 만들어야 한다.
- **경로 C.** A로 시작하되 일부 구간에서 B가 필요한 혼합형.

이 질문의 답이 나오기 전에는 엘리베이터 코드를 쓰지 않습니다. 잘못된 쪽을 만들면 통째로 버리게 됩니다. 답은 푸두 담당자 문의, 푸두 문서, 건물 관리 주체와 승강기 업체 확인에서 나옵니다.

## 단계와 통과 기준

각 단계는 기준을 통과해야 다음으로 갑니다. 로봇이 움직이거나 엘리베이터를 쓰는 단계에는 승인 게이트를 둡니다.

| 단계 | 내용 | 게이트 | 통과 기준 |
|---|---|---|---|
| 0 | 사실 확인(로봇 안 움직임) | | 경로 A/B/C가 문서와 답변으로 정해지고, 승인 범위가 서면으로 남는다 |
| 1 | 조회 전용 연결 | | 이 가이드의 03, 04가 끝나고 층별 맵과 지점이 기록된다 |
| 2 | 같은 층 지점 이동 | 현장 담당자 입회, 비상정지 접근 가능 | 두 지점 사이 10회 왕복, 도착 실패 0회 |
| 3 | 엘리베이터 시험 | 서면 승인, 승강기 업체나 관리 담당자 입회, 승객 없는 시간대 | 사람이 동행한 상태에서 2개 층 이동 5회 성공 |
| 4 | 무동행 층간 이동 | 3단계 결과를 승인 주체가 확인 | 동행 없이 5회 연속 성공 후 10회 |
| 5 | 물건 운반 | | 실제 물건으로 10회 운반, 분실과 낙하 0건 |
| 6 | 운영화 | | 문 안 열림, 통신 끊김 같은 장애에서 안전하게 멈추고 알림이 간다 |

통과 기준의 숫자는 예시입니다. 현장 사정에 맞게 바꾸되, 측정할 수 있는 값으로 유지하세요.

## 엘리베이터 탑승 상태 머신 초안 (경로 B 기준)

```
IDLE -> GO_TO_HALL -> CALL_ELEVATOR -> WAIT_DOOR
     -> ENTER -> BOARDED -> RIDE -> ARRIVED
     -> EXIT -> GOT_OFF -> NEXT_LEG 또는 IDLE
어느 상태에서든 타임아웃이나 오류가 나면 SAFE_HOLD (사람 호출)
```

엘리베이터 연동 API가 정한 단계 이름과 호출 시점은 해당 API 문서를 받아야 확정됩니다. 위 순서는 일반적인 호출, 문 열림 대기, 탑승, 하차 순서로 짠 초안입니다.

## 미리 생각해 둘 위험

- **승강기 안 통신.** 클라우드 API를 쓰므로 승강기 안에서 Wi-Fi나 LTE가 끊기면 탑승 상태를 잃을 수 있습니다. 시험 전에 층별, 승강기 안 신호를 측정하세요.
- **사람과의 충돌.** 만재 시 총중량이 360kg대입니다. 승객 우선 양보와 탑승 거부 조건(만원, 승객 탑승 중)을 규칙으로 정해 두세요.
- **비상 상황.** 화재 운전, 정전, 점검 모드에서는 로봇이 엘리베이터에 개입하면 안 됩니다.
- **승인 범위.** 회사 건물이어도 엘리베이터 조작은 건물 관리 주체나 승강기 업체의 권한일 수 있습니다.

이 계획은 진행하면서 [상태 파일](../templates/state-template.md) 양식으로 갱신합니다.
